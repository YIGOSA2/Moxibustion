# HMI 与 NFC 联调问题记录

日期：2026-07-01

## 1. 本次联调目标

本次联调的目标不是完整功能闭环，而是先打通下面这条最小链路：

```text
刷 NFC 卡 -> 屏幕切到参数页 -> 显示 UID -> 显示默认参数
```

默认参数定义为：

- 温度：`20`
- 工作时长：`0`
- 久坐时长：`0`

## 2. 当前已确认的屏幕页面与控件

参数页使用：

- 页面命令：`page 0`
- `n0`：温度
- `n1`：工作时长
- `n2`：久坐时长
- `n3`：卡编号

## 3. 串口屏通信方式确认

当前屏幕使用 `UART4` 通信，波特率已统一为：

```text
115200
```

当前命令发送方式确认如下：

- 使用文本指令
- 每条命令结尾必须发送原始字节：

```text
0xFF 0xFF 0xFF
```

特别说明：

- 不能用普通 `printf` 风格字符串去混发结束符
- 结束符必须按原始字节单独发送
- `0xff` 和 `0xFF` 在 C 语言里是同一个字节值，不是编码问题

## 4. 本次遇到的关键问题

### 4.1 串口调试输出和屏幕指令混在同一个 UART4

最开始 `UART4` 既承担调试日志，又承担屏幕命令发送，导致屏幕收到的内容被调试文本污染，无法稳定解析。

处理方式：

- 保留 `UART4` 给屏幕使用
- 屏幕命令与调试输出逻辑分开
- 目前默认关闭普通调试文本输出

### 4.2 页面切换命令使用页面编号更稳定

实际联调时发现，直接使用：

```text
page 0
```

比使用页面名更明确，因此当前按页面编号处理。

### 4.3 屏幕参数发送协议多次调整

一开始尝试用 16 位时长参数，但上位机发送高低字节顺序容易和 MCU 解析不一致，联调成本较高。

后面改成 1 字节参数协议，当前约定为：

```text
AA 55 01 03 [temp][work_time][sit_time] [xor]
```

校验规则为：

```text
0x01 ^ 0x03 ^ temp ^ work_time ^ sit_time
```

### 4.4 叠加 EEPROM 后现象变复杂

在把 EEPROM 参数保存与按 UID 查找功能接入后，出现了：

- 刷卡响应异常
- 掉电后重刷卡不稳定
- 很难快速判断是 NFC、屏幕还是 EEPROM 哪一层出问题

结论：

- 这阶段一次性叠加的逻辑过多
- 不适合继续在复杂版本上猜问题
- 必须退回到最小可工作的基线版本再逐步加回

## 5. 已验证通过的基线版本

当前已经退回并重新验证通过的最小版本是：

1. 上电初始化屏幕基础层
2. 初始化 PN532
3. 等待刷卡
4. 刷到新卡后：
   - 发送 `page 0`
   - `n3` 显示当前 UID 对应编号
   - `n0 = 20`
   - `n1 = 0`
   - `n2 = 0`

这一版已经确认可以工作。

## 6. 本次关于 EEPROM 的结论

当前不是直接否定 EEPROM 思路，而是确认：

- `NFC UID -> EEPROM 查参数 -> 屏幕回显参数`

这个方案方向没有问题；

但在实际联调时，不能一上来同时叠加：

- UID 查找
- 默认参数加载
- 参数帧接收
- 参数保存
- 掉电验证

否则一旦现象异常，很难快速锁定是哪个层面的问题。

## 7. 后续正确推进顺序

下一步建议严格按下面顺序推进：

1. 保持当前最小可工作版本不变
2. 重新接入 EEPROM 查找逻辑
   - 刷卡后只查 UID
   - 找到则显示旧参数
   - 找不到则显示默认参数
3. 屏幕“设置参数”按钮发帧后，先让 MCU 只解析并显示收到的参数
4. 确认参数帧解析无误后，再接入 EEPROM 保存
5. 保存成功后立刻回读 EEPROM 并重新回显，确认写入链路
6. 最后再做掉电重上电验证

## 8. 当前阶段结论

今天最重要的成果不是“把所有功能一次做完”，而是明确了：

- 屏幕基础通信方式
- 结束符发送方式
- 页面编号切换方式
- 参数页关键控件
- 刷卡切页的最小可工作版本

这给后面把 EEPROM 参数加载和保存重新加回提供了稳定基线。*** End Patch
